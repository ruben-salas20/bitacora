# Volver a programar salió como esperaba: cada error se resolvió mirando lo que llegaba de verdad, no suponiendo
---
### **Qué hice**
Empecé el proyecto `harness` en `~/Work/harness`: un chat en Python contra mi modelo local de ai-lab (llama-swap, `gemma-4-e4b-rapido`), con la idea de acabar construyendo un agente y publicarlo en GitHub como portfolio. Yo escribía el código y ejecutaba; la IA guiaba paso a paso sin darme la solución. Tenía abierta por mi lado la documentación de httpx.

**Explorar la API a mano, antes de programar.** `curl -s https://llama.rubensalas.dev/v1/models | jq` para ver los modelos, y después un POST a `/v1/chat/completions` con `-H "Content-Type: application/json"` y el cuerpo en `-d` (`model` + `messages`). De ahí saqué el camino al texto: `choices[0].message.content`.

**Crear el proyecto.** `uv init harness` y `uv run harness`, que creó `.venv` con CPython 3.13.15 y `uv.lock`. Cambié el email por el de mi cuenta de GitHub en `pyproject.toml` y en `git config --global user.email`, antes del primer commit.

**Primer código.** `uv add httpx` y, en `main()`, `httpx.post(url, json=cuerpo)`, `.json()` e indexado. Falló con `KeyError`; añadí `print(respuesta.status_code)` y `print(datos)` y así encontré los dos errores.

**Timeout.** `curl -s .../unload` seguido de `uv run harness`, que no falló. Repetí con `unload`, `curl -s .../running | jq` (lista vacía) y `time uv run harness` dos veces seguidas. Después forcé `timeout=1` para ver el error y lo dejé en `timeout=30`. Añadí `respuesta.raise_for_status()` antes de `.json()` y lo probé con un nombre de modelo inventado.

**Fase 2.** Bucle con `input("> ")` y `salir`. Primero sin memoria (el modelo no recordaba mi nombre) y después con la lista `mensajes` creada fuera del bucle, haciendo `append` de `user` y `assistant` e imprimiendo `usage.prompt_tokens` en cada turno. Llené el contexto a propósito con `uv run python -c` y `"hola " * 40000`. Añadí un system prompt con concatenación implícita de strings y lo comparé repitiendo la conversación.

**Streaming.** Primero lo miré en crudo con `curl -N` y `"stream": true`. Luego en Python: `"stream": True` y `"stream_options": {"include_usage": True}` en el cuerpo, `with httpx.stream("POST", ...) as respuesta`, `iter_lines()`, saltar líneas vacías, cortar en `data: [DONE]`, `json.loads(linea.removeprefix("data: "))`, `.get("usage")`, `.get("content")`, `print(..., end="", flush=True)` y guardar el texto acumulado como `assistant`. Para depurar usé `print(repr(linea))` y el intérprete (`uv run python`).

**Herramientas.** `uv add --dev ruff`, `[tool.ruff.lint] extend-select = ["W", "N", "B", "UP"]`, `uv run ruff check --fix` revisando con `git diff`, y `uv run ruff format --diff` antes de `uv run ruff format`. En Neovim activé `lang.python` con `:LazyExtras` (pyright + ruff) y añadí `[tool.pyright]` con `venvPath = "."` y `venv = ".venv"` en `pyproject.toml`.

Quedaron 10 commits separados por idea, con Conventional Commits (`chore`, `feat`, `fix`, `style`).

### **Qué esperaba**
Miedo no, pero sí sentía que iba a tener problemas con el código por no recordar muchas cosas, y usar librerías nuevas que no conocía era una sensación rara. Aun así esperaba ser capaz de hacerlo: aprender, investigar y, poco a poco, mejorar mis habilidades.

### **Qué pasó**
Se cumplió lo esperado. Hubo momentos en los que la lógica me costaba por falta de práctica, pero poco a poco se fue resolviendo. Al final de la sesión tenía un chat con memoria, system prompt y respuestas en streaming contra mi modelo local, más ruff y pyright configurados. Los errores eran esperables, porque son parte del proceso.

**El primer código falló sin decir por qué:**

    KeyError: 'choices'

Imprimiendo la respuesta apareció `404` y un JSON que decía que el modelo al que se enrutaba la solicitud no existía.

**La predicción del timeout falló.** Se esperaba un `ReadTimeout` al pedir con el modelo descargado, y no salió ningún error. Medido:

    real    0m4,722s   ← modelo descargado
    real    0m0,374s   ← modelo ya cargado

Con `timeout=1` sí apareció, al final de un traceback de ~70 líneas cuya única línea mía era `__init__.py, line 12`:

    httpx.ReadTimeout: The read operation timed out

**Llenar el contexto:**

    400
    {"error":{"code":400,"message":"request (40009 tokens) exceeds the available context size (32768 tokens), try increasing it","type":"exceed_context_size_error","n_prompt_tokens":40009,"n_ctx":32768}}

**La memoria se ve crecer.** `prompt_tokens` por turno sin system prompt: `15 → 49 → 67 → 100 → 252 → 295 → 362`. El salto 100 → 252 vino de una respuesta larga del modelo que ya estaba en el historial. Con el system prompt de concisión llegué a 228 en el mismo punto de la conversación, con un turno más.

**El streaming se atascó dos veces:**

    json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)

y, después de "arreglarlo" con `if "" in linea: continue`, el bucle se saltaba todas las líneas.

**Neovim, al activar pyright:**

    Import "httpx" could not be resolved

### **Por qué**
**`KeyError: 'choices'`:** la URL era `/v1/completions` en lugar de `/v1/chat/completions`, y el modelo era `gemma-6-e4b-rapido` en lugar de `gemma-4-e4b-rapido`. llama-swap revisa primero el modelo para enrutar, así que el error solo contaba ese problema. El `KeyError` era el síntoma: el código indexaba un JSON de error como si fuera una respuesta buena.

**El timeout no saltó** porque httpx espera 5 s por defecto y la carga del modelo tarda unos 4,3 s. Funcionaba por medio segundo.

**`JSONDecodeError (char 0)`:** SSE manda una línea vacía entre eventos e `iter_lines()` también la entrega. Yo creía que las "líneas vacías" eran el espacio entre `data:` y el JSON. **`"" in linea` es siempre verdadero:** el string vacío está contenido en cualquier string. Lo que tocaba era `linea == ""`.

**Me costó el `for` del streaming** porque no sabía manejar bien cómo validar qué información estaba llegando en cada trozo: control de diccionarios, sobre todo con las claves que a veces vienen y a veces no (`content` en `null`, `delta` vacío, `choices` vacío en el trozo de `usage`). Una vez lo entendí, salió.

**`httpx could not be resolved`:** pyright lo arranca Neovim, no `uv run`, así que buscaba librerías en el Python del sistema y no en `.venv`.

**Por qué el modelo carga en ~4,3 s: `Sin resolver`.**
- *Hipótesis:* la caché de páginas de Linux en ai-lab. El archivo `.gguf` (~3 GB) sigue en RAM desde la carga anterior y se lee sin tocar el disco.
- *A favor:* `unload` vacía la VRAM, así que la GPU no conserva nada entre cargas; lo que puede ir rápido es la lectura del archivo.
- *En contra:* no se midió nada. Podría ser simplemente un disco rápido.
- *Por qué se perdió el rastro:* no se reinició ai-lab ni se vació la caché antes de medir.

### **Qué me llevo**
- **Antes de programar contra una API, probarla a mano** (curl o similar) y leer la respuesta en crudo. El código solo traduce algo que ya vi funcionar.
- **En un traceback, leer la última línea (qué pasó) y buscar las líneas de mi propio código (dónde).** Lo que pasa por librerías casi nunca es el fallo.
- **Si los datos no son lo que espero, imprimirlos antes de usarlos**, con `repr()` si puede haber algo invisible. El error suele saltar después de la causa.
- **Un mensaje de error cuenta el primer problema que encontró, no todos.** Corregir y volver a ejecutar.
- **Si algo funciona por poco, medirlo** y compararlo con el límite. Si mi caso depende de un valor por defecto, fijarlo explícitamente.
- **Si una herramienta no encuentra algo que sí está instalado, preguntar qué entorno está mirando.** Vale igual para un editor, un contenedor o un cron.
- **Lo mecánico (formato, estilo) lo hace una herramienta, y reviso el diff de lo que cambia.** La lógica sigue necesitando leerla yo: ruff no detectó un `if` redundante.
- **`pyproject.toml` es lo que quiero y `uv.lock` es lo que se instaló.** El lock se versiona; el entorno no.
- **Tener la documentación oficial abierta mientras programo y consultarla antes de preguntar.** Así aprendo a buscar por mi cuenta y no dependo solo de que alguien me responda.
