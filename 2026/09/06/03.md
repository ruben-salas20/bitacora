# Primer PR a open source: el fix estaba bien escrito, el diagnóstico no
---
### **Qué hice**
Quise contribuir a [Monocode](https://github.com/hardbeat920/monocode) (app Tauri, Rust + TS) por una ventana de consola que parpadeaba cada cierto tiempo en Windows 11. Diagnóstico inicial: `gh_run()` en `src-tauri/src/fs.rs` no protegía el spawn de `gh`. Fix de una línea en `fs.rs:2490`:

    crate::hide_window_console(&mut cmd);

Verificación y publicación:
- `npm run check:rust` → cargo fmt + clippy `-D warnings` + 174 tests, verde
- `npm run check:web` → vitest 1282 tests + `tsc --noEmit`, verde
- `git commit -m "fix(windows): hide console window when spawning gh"`
- `gh pr create --repo hardbeat920/monocode` → [PR #100](https://github.com/hardbeat920/monocode/pull/100), sobre el [issue #96](https://github.com/hardbeat920/monocode/issues/96) que abrí yo
- `npm run build:windows` (`tauri build --bundles nsis`) e instalé mi propia build

### **Qué esperaba**
Entendiendo lo hecho y viendo que tenía sentido, asumí que estaría correcto y que el mantenedor haría merge, porque cumplíamos todos los requisitos.

### **Qué pasó**
Instalé mi build con el fix y la ventana seguía apareciendo. El cambio era un no-op. Cerré el PR #100 y corregí el issue #96.

La causa real no estaba en MonoCode:

    gh.exe              <- CREATE_NO_WINDOW: consola invisible (MonoCode, correcto)
    └── gh send-telemetry   <- DETACHED_PROCESS: sin consola (gh, acá se rompe)
        └── tzutil.exe /g   <- programa de consola sin consola que heredar
                               -> Windows le crea una nueva, VISIBLE

Ya estaba reportado y arreglado: `cli/cli#13354`, PR #13353, mergeado el 2026-05-13. Yo tenía `gh 2.92.0` (2026-04-28), anterior al fix. Solución: actualizar `gh`.

### **Por qué**
Había otra función que se encargaba de blindar que `gh` no generara una nueva ventana (`apply_gui_env` llama a `hide_window_console` en `harness.rs:1826`), pero no se indagó lo suficiente y asumimos que el error era ese. Cuando hicimos el supuesto fix y vimos que seguía sucediendo, nos dimos cuenta de que teníamos que haber explorado más allá desde el principio.

### **Qué me llevo**
- Antes de concluir que a un archivo le falta algo, seguir las funciones que llama. Un `grep` que no encuentra el nombre no prueba que la protección no esté entrando por otra capa.
- Un CI en verde y una plantilla completa no validan el diagnóstico. Solo dicen que el código compila y que seguí el proceso.
- Si aplico el fix y el síntoma sigue, el que estaba mal era el diagnóstico. Probar el arreglo contra el síntoma real ANTES de publicarlo.
- Un mal diagnóstico lleva a un fix inservible; un buen diagnóstico lleva al fix necesario.

De Rust (venía de Python básico, nunca había tocado Rust):
- `&mut x` es prestar para modificar; `&x` prestar para leer; `x` a secas cede el valor y el que llamó se queda sin nada.
- `#[cfg(windows)]` no es un `if` de ejecución: borra el bloque al compilar. Los problemas aparecen en la plataforma que no estoy mirando.
- Un `use` de un trait puede ser obligatorio aunque el nombre no se use en el archivo: sin él, el método que agrega no existe.
- `Command` es una receta, no un proceso. Los flags van antes de `.output()`.
